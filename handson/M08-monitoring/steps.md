## パート 2: 応答品質のモニタリング（15分）

### ステップ 2.1: ハルシネーション検出

```bash
python3.12 hallucination_detection.py
```

検出手法：
1. **一貫性チェック**: 同じ質問への回答が矛盾していないか
2. **ソース検証**: RAG の場合、回答がソースに基づいているか
3. **エンティティ検証**: 生成された固有名詞・数値の妥当性
4. **信頼度スコア**: モデルの不確実性を数値化

### ステップ 2.2: 品質スコアダッシュボード

CloudWatch ダッシュボードに表示するメトリクス：
- Faithfulness Score（忠実性スコア）
- Answer Relevancy（回答関連性）
- Hallucination Rate（ハルシネーション率）
- Response Completeness（回答の完全性）

### ステップ 2.3: 回答パターン分析（長さと複雑さのモニタリング）

```bash
python3.12 response_pattern_analysis.py
```

パターンベースの検出手法：
1. **回答の長さの異常検出**
   - カテゴリ別ベースラインからの偏差（Z-score）
   - 異常に長い回答 → 情報の水増し、関係ない内容の生成
   - 異常に短い回答 → 知識不足を曖昧に回避

2. **複雑さのパターン分析**
   - 繰り返し（ループ）検出: 同じフレーズの反復
   - コヒーレンス分析: 文間の論理的つながりの低下
   - 情報密度: 修飾語だけで実質的な情報がない状態の検出

3. **統合リスク判定**
   - 長さ異常 × 複雑さ異常 → ハルシネーション疑いスコア
   - CloudWatch メトリクスとして発行

しきい値の設定（ベストプラクティス）：
- 控えめに始めて誤検出に基づいて調整する
- ユースケースごとに許容幅を変える（クリエイティブ系 vs 医療系）
- 最初の2週間は「観察モード」で誤検出率を確認

### ステップ 2.4: アラートルールの設定

- ハルシネーション率 > 5%: 警告
- ハルシネーション率 > 10%: 緊急（モデル切り替え検討）
- レイテンシー P95 > 10秒: 警告
- エラー率 > 1%: 緊急
- 繰り返しスコア > 0.3: ループ検出アラート
- コヒーレンススコア < 0.3: 品質低下アラート

### ステップ 2.5: 推論経路分析と論理エラー検出

```bash
python3.12 reasoning_analysis.py
```

AIロジックの透明性フロー（4段階）：
1. **Level 1: ブラックボックス** — 通常の回答（推論過程なし）
2. **Level 2: 思考の連鎖（CoT）** — ステップバイステップの推論を表示
3. **Level 3: 構造化推論** — JSON形式で検証可能な推論ステップ
4. **Level 4: 説明可能な回答** — ユーザー向けに信頼度付きで提示

体系的な論理エラーの検出：
- **循環論法**: 結論を使って前提を正当化していないか
- **誤った前提**: 事実と異なる初期前提に基づいていないか
- **一貫性の欠如**: ステップ間で矛盾がないか
- **非論理的飛躍**: 前提から結論が論理的に導かれているか

相互検証（クロスバリデーション）：
- 正方向の推論と逆方向の検証を比較
- 結論が崩れるケース（反例）を自動探索
- 推論の信頼性を多角的に評価

## パート 3: ビジネス影響の測定（10分）

### ステップ 3.1: ビジネスメトリクスの定義

```bash
python3.12 business_metrics.py
```

3つの柱：
1. **ユーザーエンゲージメント**
   - セッション数、対話ターン数
   - 会話完了率 vs 離脱率
   - リピート利用率

2. **タスク完了**
   - 問題解決率（最初の回答で解決）
   - エスカレーション率（人間への転送）
   - 平均解決時間

3. **ROI**
   - コスト削減額（人件費との比較）
   - 処理件数の増加
   - 顧客満足度スコア（CSAT）

### ステップ 3.2: ROI 計算フレームワーク

```
ROI = (Total Benefits - Total Costs) / Total Costs × 100%

Benefits:
  - 自動解決による人件費削減: ¥X/月
  - 処理速度向上による効率改善: ¥Y/月
  
Costs:
  - Bedrock API コスト: ¥A/月
  - インフラ運用コスト: ¥B/月
  - 開発・保守コスト: ¥C/月
```

## パート 4: インテリジェントアラートシステム（10分）

### ステップ 4.1: 知性フィルターの実行

```bash
python3.12 intelligent_alert_filter.py
```

知性フィルターの判定ロジック：
- **コンテキスト認識**: 営業時間・曜日パターン・計画イベントに基づくベースライン動的調整
- **アラート抑制**: 単発の外れ値は無視し、連続3回以上の異常のみエスカレーション
- **計画イベント連携**: リリース日やキャンペーン期間中のスパイクを自動的に「想定内」と判定

### ステップ 4.2: シナリオ別の判定結果を確認

8つのシナリオで知性フィルターの効果を確認：

| シナリオ | 値 | 判定 | 理由 |
|---------|-----|------|------|
| 営業時間の正常トラフィック | 250 req/h | 抑制 | 正常範囲内 |
| 計画イベント中のスパイク | 12000 tokens/min | 抑制 | リリース日の想定範囲 |
| 深夜3時のリクエスト | 150 req/h | CRITICAL | 不正アクセスの疑い |
| トークン急増（単発） | 800 tokens | 抑制 | 単発の外れ値 |
| トークン急増（連続3回目） | 850 tokens | WARNING | 連続異常 → 傾向レポート |
| エラー率急騰 | 25% | CRITICAL | ベースライン5倍超 |

### ステップ 4.3: 3層エスカレーションの設計

```
即時（CRITICAL）  → PagerDuty / オンコールエンジニア
まとめ（WARNING） → Slack チャネル / 傾向レポート
戦略的（INFO）    → 月次レポート / 経営ダッシュボード
```

ポイント:
- 同じ値 150 req/h でも、営業時間なら正常、深夜なら即時アラート
- 抑制率を確認し、無駄なアラートによるオペレーター疲弊を防止
