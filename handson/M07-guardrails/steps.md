プロンプトキャッシングの仕組み：

- `cachePoint` マーカーを使用してキャッシュ境界を指定
- キャッシュヒット時はトークンコストが大幅削減（最大90%）
- キャッシュ TTL: 5分

### ステップ 1.2: 3回のリクエストで効果を確認

1. **ベースライン**: キャッシュなしの通常リクエスト

3. **キャッシュヒット**: 同じプレフィックスで別の質問（大幅なコスト削減）

結果の確認ポイント：
- cache_read_tokens > 0 でキャッシュヒットを確認
- トークン削減率（通常 85-95%）
- レイテンシー改善（通常 40-60%）

## パート 2: セマンティックキャッシュ（15分）

### ステップ 2.1: 概念と実装

```bash
python3 semantic_cache_demo.py
```

従来キャッシュ vs セマンティックキャッシュ：
- 従来: 完全一致のみ → 「パスワードリセット方法」≠「ログイン情報の変更手順」
- セマンティック: 意味の類似度で判定 → 両方キャッシュヒット

### ステップ 2.2: 実装パターン

```
ユーザークエリ → 埋め込みベクトル生成 → キャッシュ検索（類似度）
  → ヒット: キャッシュ応答を返却（APIコール不要）
  → ミス: Bedrock呼び出し → 応答をキャッシュに保存
```

類似度しきい値のチューニング：
- 0.95以上: 高精度（ヒット率低、品質高）
- 0.85以上: バランス（推奨）
- 0.75以上: 高ヒット率（品質リスクあり）

### ステップ 2.3: キャッシュ無効化戦略

- TTL ベース: 5分〜24時間（コンテンツの鮮度に応じて）
- イベントベース: ナレッジ更新時に関連キャッシュを無効化
- バージョンベース: モデル変更時に全キャッシュをクリア

## パート 3: 動的バッチ処理とスケーリング（10分）

### ステップ 3.1: キュー深度に応じた動的バッチサイジング

```bash
python3 batch_optimization.py
```

スケーリングルール：
- レイテンシー優先モード（<50 pending）: バッチ5、即時処理
- バランスモード（50-500 pending）: バッチ25、5秒バッファ
- スループットモード（>500 pending）: バッチ50、10秒バッファ

### ステップ 3.2: コスト自動管理

予算超過時の自動アクション：
1. 警告しきい値（80%）→ アラート送信
2. 制限しきい値（95%）→ 高コストモデルから低コストモデルへ切り替え
3. 上限しきい値（100%）→ 新規リクエストをキューイング
